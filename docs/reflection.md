# FieldSignal AI — Project Reflection

*CDF Energy AI Hackathon · 2026*

---

## What Was Built

FieldSignal AI is an executive-grade energy intelligence dashboard that ingests a decade of U.S. EIA crude oil and natural gas production data, computes analytics in the browser, and layers in a Claude-powered AI analyst for contextual Q&A.

The final product has seven functional zones:

1. **KPI Band** — five headline metrics (total output, top producer, YoY trend, active states, 2028 projection)
2. **Choropleth Map** — interactive Mapbox GL map where clicking a state focuses all panels on that region
3. **Compare Panel** — side-by-side oil and gas metrics for any two states
4. **Production Trend + Forecast** — historical bar chart with optional CAGR forecast overlay to 2030
5. **Strategic Intelligence** — Action Center (six heuristic alerts) and Claude AI Analyst
6. **Scenario Simulator** — Downside / Base / Upside 2028 projections with a CAGR slider
7. **Well Economics Calculator** — single horizontal well financial model with decline curve, NPV, IRR, payback, and breakeven outputs

All analytics run on the client with no secondary API calls except the optional AI analyst stream.

---

## What Changed After the Scope Update

The initial plan covered KPIs, a production chart, a map, year-range filtering, AI analyst, and state comparison. Everything on that list shipped on schedule.

Three expansions happened after the core was complete:

**Scenario Simulator**: The forecast chart alone didn't address the "what if growth slows?" question that any strategic user would ask. Adding three named scenarios (Downside / Base / Upside) with a manual CAGR slider turned a passive chart into an interactive planning tool.

**Action Center with 6 heuristic alerts**: An early version surfaced a single "top insight." That felt too thin — executives need ranked, actionable signals, not a summary paragraph. Replacing it with six independent deterministic checks (concentration risk, production decline, coverage gap, forecast fragility, state outperformance, strong growth) made the intelligence layer genuinely useful and explainable. Each alert shows the exact condition that triggered it.

**Well Economics Calculator**: Added as a stretch feature in the final milestone. The motivation was practical: an analyst evaluating a new-basin investment needs to think about single-well economics, not just aggregate output trends. The calculator gives them a quick-and-dirty IRR/NPV estimate directly in the dashboard, with basin-representative presets that auto-load when a state is focused on the map.

## Why Certain Product Decisions Were Made

**No database.** The production dataset is ~200 records. Introducing a database would have added deployment complexity (connection strings, migrations, pooling) for zero functional benefit. A checked-in JSON file, regenerated by a Python script, is simpler, faster, and fully reproducible.

**No Recharts.** The production trend and well economics charts are simple enough to render as HTML flex containers with computed heights. Recharts would have added bundle weight and introduced its own abstraction layer. The one exception is the cumulative cash flow chart, which crosses zero — that needed an inline SVG to handle negative values cleanly without a library.

**CAGR model instead of ML.** A data science model — ARIMA, LSTM, or a vendor API — would have added a dependency and made the forecast logic opaque. A CAGR with explicit clamping, a quality score, and a methodology strip is transparent, fast, and honest about its limitations. Analysts can reason about what it's doing.

**Pre-computed context for Claude, not raw data rows.** Sending 200 production records to the API on every question would be slow, expensive, and redundant. The `AnalystContext` object sends the 7 numbers Claude actually needs to answer the questions analysts ask. The constraint that Claude cannot invent numbers it wasn't given is enforced by the system prompt.

**Preserving oil price and discount rate across state presets.** When a user focuses Texas, the well economics presets load Permian Basin IP rate, decline, capex, and LOE. But oil price and discount rate stay unchanged. These are economic assumptions the analyst owns — they shouldn't be overwritten by a state click.

## How AI Tools Were Used During Development

Claude was used as a development collaborator throughout the build. Specifically:

- **Architecture decisions** — worked through the server/client split, the context injection pattern for the analyst, and the IRR bisection approach in dialogue with the model
- **Math verification** — the closed-form breakeven price derivation (NPV = 0 solved for price) was verified iteratively against the numerical path
- **Component API design** — drafted prop interfaces for `ScenarioSimulator`, `BoardBriefModal`, and `WellEconomicsCalculator` in conversation before implementing
- **Documentation** — all submission docs (this file included) were written with Claude assistance, starting from the actual codebase state

The Claude AI Analyst panel in the product itself was designed to reflect how the tool should actually be used: grounded in real data, structured to separate fact from inference, and transparent about its limits.

## Technical Tradeoffs

**Forecast horizon to 2030, not 2028**: The UI originally targeted 2028. The ForecastPanel extends to 2030 by default (configurable via `horizonYear`). The scenario simulator and KPI band use 2028 as the headline number. Both are consistent.

**IRR bisection**: A Newton-Raphson approach would converge faster, but bisection is simpler to reason about and immune to the derivative-near-zero failure mode that Newton's method hits on flat NPV curves. 120 iterations at double precision is effectively exact.

**Hardcoded scenario CAGRs**: The base CAGR assumptions (Downside −2%, Base +2.5%, Upside +5.5%) are hardcoded constants in `lib/scenario.ts`. They are not derived from the historical data. This was intentional — scenario analysis requires stable reference points, not values that shift with the year filter.

**Single-step state focus sync**: All downstream panels react to `focusedState` in `DashboardClient`. This is clean but means a state click triggers multiple `useMemo` recomputations simultaneously. For 200 rows of data, this is imperceptible.

## What Was Intentionally Simplified

**Oil only for forecast and scenario**: Gas production data is ingested and shown in the Compare panel, but the forecast, scenario simulator, and well economics are oil-only. Gas requires separate decline parameters and price assumptions. Adding dual-commodity support would have doubled the complexity of the financial model without adding proportional clarity.

**No royalty, tax, or NGL in well economics**: The model is `revenue = production × oil price`, `NCF = revenue − LOE`. Real well economics include severance taxes, royalty burdens, and NGL revenue. These were excluded deliberately — the goal is a directionally useful illustrative tool, not a rigorous AFE model.

**No operator-level data**: The EIA dataset is state-level aggregates. Operator-level production data (from Enverus, DrillingInfo, etc.) would add substantial cost and complexity.

**No user authentication**: All state is client-side and session-scoped. There is no saved analysis, no user accounts, and no shared dashboards. For a hackathon demo, this is appropriate.

## What Would Be Built Next with More Time

1. **Gas economics tab**: Extend the well economics calculator to handle gas wells with separate IP rates, decline curves, and Henry Hub pricing.
2. **Multi-well portfolio aggregation**: Stack multiple well scenarios into a portfolio-level NPV, allowing "what does a 10-well Permian program look like?"
3. **Operator-level map layer**: Overlay top operators by state using publicly available EIA or state regulatory data.
4. **Saved scenarios**: Allow analysts to name and save scenario configurations for comparison across sessions.
5. **Live EIA data refresh**: Replace the manual Python script with a scheduled background refresh on the hosting platform.
6. **Export improvements**: Export the scenario simulator output to CSV; add a PDF render option for the Board Brief.
7. **Mobile layout**: The current design is optimized for wide viewports. Responsive breakpoints for tablet/mobile would broaden the audience.

## Key Lessons Learned

**Explainability is a feature, not a disclaimer.** The most-used part of the Action Center is the explanation text under each alert, not the alert title. Users want to know *why* something fired. The same applies to the quality score in the Confidence Strip — surfacing the methodology builds trust.

**Server/client split needs to be decided early.** The constraint that `lib/eia.ts` is server-only (it reads from disk) and `MapPanelClient` is client-only (Mapbox requires browser APIs) shapes the entire component tree. Discovering this late would have required significant refactoring.

**Streaming makes AI feel fast.** The Claude response latency is 1–3 seconds to first token. Without streaming, the chat panel would show a blank UI while waiting. With streaming, users see the response building in real time — a qualitatively different experience even if the total latency is identical.

**Simple models with honest uncertainty > complex models with false confidence.** The CAGR forecast is naive. But it ships with a quality score, a methodology note, and clear "Illustrative model" labels everywhere. An analyst knows exactly what they're getting. A black-box ML model with a polished UI but no explainability would be less trustworthy, not more.
